# C1 — proveedores confirmados y borrador

**Cambio aprobado el 2026-10-02:** backend Go y frontend TypeScript/Next.js.
La [decisión final de stack](2026-10-02-stack-go-frontend-ts.md) sustituye el backend
TypeScript mencionado en este documento. La adaptación del candidato L3,
despliegue, workflows y validación Go sigue pendiente antes de C2.

**Presupuesto indicado por Diego:** hasta US$250/mes de infraestructura inicial.
**Objetivo:** preparar L3 V8 sobre Next.js y TypeScript, con PostgreSQL y workflows
administrados. El [programa aprobado](2026-09-25-habilitar-r0-design.md) mantiene
la elección de proveedores en C1 y la emisión canónica en C2.

## Elección confirmada — 2026-09-30

Supabase Pro para base de datos y autenticación, Small + PITR de siete días para
R1; Trigger.dev Hobby para workflows; Vercel Pro para Next.js; almacenamiento
privado con copia independiente; Upstash para límites de frecuencia no patrimoniales.
El ticker de Supabase Cron conserva el despacho del outbox cada diez segundos.

Diego confirmó Supabase Pro + Trigger.dev + Vercel Pro el 2026-09-30 en esta
conversación. Se mantienen los ajustes de autenticación documentados y PostgreSQL 17
condicionado a validar el esquema. Esto elige la arquitectura; no acredita esa
validación, no contrata servicios ni garantiza una factura fija.
Neon queda como alternativa si la validación del proveedor elegido falla.

**Pagos e identidad:** Mercado Pago elegido; Truora priorizado para evaluación
KYC/KYB, con alcance empresarial y precio pendientes. No son servicios contratados.

## Estado de decisiones antes de C2

1. **Confirmado:** Supabase + Trigger + Vercel con un presupuesto operativo objetivo de US$215 antes
   de impuestos, dejando US$35 de margen para impuestos y variación; consumo real
   debe vigilarse. Alternativa: Neon + servicios separados, aún sin total cerrado.
2. **Confirmado condicionalmente:** evaluar PostgreSQL 17; la migración debe pasar antes de C2.
3. **Confirmado para el borrador:** contrato de sesión aplicativa de la nota de seguridad, sin asumir
   equivalencia literal entre la auth de Supabase y L3 V7.
4. Aprobar como objetivos iniciales RPO DB≤5min y RTO ≤4 h para R1, sujetos a ensayo;
   son objetivos del sistema, no SLA comprado ni cumplimiento demostrado.
5. Para evidencia: copia independiente y versionado antes de usar documentos reales;
   retención legal y necesidad de Object Lock pendientes de dictamen [LEGAL→ABOGADO].

La elección de proveedores es una decisión de arquitectura/presupuesto; no reactiva
la revisión humana obligatoria del desarrollo, que sigue suspendida.

## Estado honesto del borrador

Existe un candidato completo L3 V8, **no emitido**, y un overlay SQL no crítico
probado sobre V7; todavía no existe una migración completa consolidada de C1.
El SQL V8 recibido en Cowork es otra entrada, con contraejemplos de integridad
abiertos; no sustituye ese entregable. El corpus del repo no cambia.
El borrador OpenAPI cubre 61 operaciones inventariadas más 31 auxiliares con fixtures;
no acredita un backend implementado ni cierre de adaptadores o decisiones pendientes.
No se inicia código de producto ni se levanta el freeze.

Las migraciones críticas, triggers de incompatibilidad en ejecución, contabilidad,
concurrencia y motor/verificador de sorteo siguen siendo implementación humana.
El borrador especifica su aceptación sin generar ese código. Diego es el dueño
actual; no se inventa un segundo revisor ni se bloquea por la suspensión de revisión.
Los vectores de sorteo requieren valores calculados por una implementación humana
independiente: no se fabrican resultados esperados para hacer pasar una prueba.

El registro CD-07 de este paquete es local. No se asignan números CHANGE/DEC del
doc20 de Outline ni se afirma haberlo actualizado. Su correlación se hará al emitir.
ASS-001 y confirmación contable permanecen abiertos; no se decide custodia aquí.
